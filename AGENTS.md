# Jobe: Career Intelligence Skill

Full pipeline job search automation for any profession: discover, evaluate, tailor a resume, apply, track, follow up, prepare for interviews, analyze.

Nothing in the code or the modes assumes a field, a country, a work arrangement, or a seniority level. Everything personal comes from the active user's workspace. Owner style hard rules (work mode, country, recency window, title levels to drop, salary floor, names that must never be printed) are configurable through `data/profile.json`; none is a constant.

## Commands
```
/jobe onboard [name]                Guided setup interview; writes every personal file. Run first.
/jobe use <name> | /jobe users      Switch or list workspaces (several people, one machine)
/jobe find                          Discover jobs under the user's own policy, verify, then generate resumes for top matches
/jobe [URL]                         Evaluate a posting with blocks A to G, generate resume and cover letter
/jobe [company] [role]              Same, finds the posting first
/jobe batch url1 url2 ...           Evaluate several postings
/jobe apply [slug]                  Fill and submit one application through the Camoufox harness; glance before submit, email confirm loop
/jobe apply-all                     Process the apply queue through the harness; --top N, --paste (fallback), --headful
/jobe apply-assisted                Fallback: paste ready blocks for forms behind a sign in wall
/jobe tracker                       Pipeline view, stats, conversion rates, orphan check
/jobe interview-prep [company]      STAR+R story mapping and likely questions
/jobe followup                      Follow up cadence and message drafting
/jobe patterns                      Application history analytics
/jobe contacto [company]            LinkedIn outreach drafts (4 contact types, 300 characters)
/jobe deep [company]                6 axis company research
/jobe project [path]                Portfolio project evaluation
/jobe linkedin-tab                  Ingest the user's open LinkedIn Jobs tab (read only, Chrome extension)
/jobe linkedin-search               Drive the user's signed in LinkedIn search and paginate (opt in, user present); also find --linkedin
/jobe calibrate                     Judge versus human scoring calibration (Cohen's kappa)
/jobe audit                         Bias audit of the scorer (name and school perturbation)
```

## Key Design Decisions

* **No field assumption, permissive when data is missing.** No role title pattern, no skills table, no employer key, no curated employer list in code or mode text. Role vocabulary comes only from the user's seeds (`lib/role-queries.js`), skills only from the user's library and baseline, policy only from `data/profile.json`. Missing user data means keep everything, score neutral, and a source returns `[]` and logs. Examples in modes and templates come from at least two unrelated professions (for example a registered nurse and a tax accountant) or are omitted.
* **Policy is data.** Work modes, countries, recency, title exclusions, salary floor, staffing filter, forbidden terms, and page target are profile keys. When adding a rule that sounds like a personal preference, add a profile key with a permissive default; never a constant. A new user file needs: a template, a scaffold line in `scripts/user.js`, a writing step in `modes/onboard.md`, a `.gitignore` line, a `DATA_CONTRACT.md` row.
* **The score is fit only.** `fullScore` measures how well the role's stated requirements map to the user's actual evidence: `34 + 44 * coverage`. `coverage` blends two estimates by `ratedness` = rated terms in `skills.levels` / 40, capped at 1, times the share of rated weaknesses / 0.2, capped at 1 (a rated term is a weakness in full at 0.5 or below, in proportion up to 0.6; nothing rated = derived only): the derived estimate, itself pulled toward 0.5 by ratedness, counts as 8 * (1 - ratedness) rated skills next to the rated skills the JD names, and each of those counts by `trust` = min(1, mean over rated terms of max(0, 0.9 - level) / 0.12), so a table of strengths alone is not counted as a rating (its terms still count as evidence that the user holds the skill, at the level given, so a posting that names rated skills the bullets do not carry scores a point or two higher for each one, about twelve for a table of ten, and can cross the 55 floor). On a posting whose title names no target role word, both measures are multiplied by min(1, max(derived / 0.5, min(1, (rated skills named - 1) / 2) * min(1, derived / 0.25))), so three rated skills named halve the coverage the posting needs and never open the table by themselves. A rated term is also evidence, so the table should hold only skills specific to the user's field, not words every field uses, and not general tools and methods that other fields share (spreadsheets, SQL, reporting, data analysis, forecasting, process improvement, project management, automation): a short posting from another field built around six or more of them is still scored by them. Rated: the mean level of the user's rated skills the JD names (0.5 when it names none). Derived: the share of the JD's own content words found in the user's evidence, stretched so 0.16 is none and 0.82 is full, and pulled toward 0.5 in proportion for a description under 60 content words. Evidence levels: bullet words up to 1.0 (in a library of hundreds of bullets a word is full evidence only when several bullets carry it), skills block or evidence index 0.6, declared gap 0.2. Pay, benefits, equal opportunity, how to apply and working condition text, employer voice sentences with no ask, and closing side sections are not counted. Plus small bonuses capped at 8 together: differentiators (`1.2 * n ** 0.75` for the n skills rated 0.9 or above in `skills.levels` that the JD names) and target role words in the title (3 each, scaled by 1 - ratedness); differentiator points are added in full only as far as the table is trusted, and for the untrusted share they take the place of title role points; plus 3 for a seniority word the user's own seeds carry; minus requirement blockers the user's known facts do not meet and 6 per unmet stated minimum. `gate1` = score >= 55, the JD left enough to judge, and coverage >= 0.5 * ratedness. A user with no skills on file has a neutral fit part of 56; only the title bonuses move it (target role words up to 8, a seed seniority word 3, so at most 67), nothing reaches the automatic band, and the find mode lists the rows and asks. It also asks, instead of auto evaluating the 80 band, whenever `skills.levels` is empty. No preference, company type, or career direction boost: preference layers were tried and removed. Preferences belong in filters. `gatePass` = `{ gate1, gate2, minimums }`, and `minimumsUnmet` is surfaced next to the score.
* **Title policy is a discovery filter, never a score modifier.** `discovery.titleExclude` and `titleKeep` are applied inside `rank.isRoleMatch(title, profile)`, so the pipeline, the manual ingest, and the agent import inherit it. A title is dropped when an exclude phrase matches outside every keep phrase (a keep phrase shields only its own words). No exclusion ships. Never call `isRoleMatch(title)` with one argument in a source: with no profile it keeps every title.
* **Work mode, country, and region are two stage gates driven by the profile.** Before enrichment a posting is dropped only when it is already known to be outside the policy; unknown is kept so enrichment can verify. After enrichment the strict pass decides on the real job description; a posting that still states no work mode then counts as onsite. For a country list other than exactly `["US"]` a posting is dropped only when its location names a country outside the list (or is recognizably in the US); a city alone, or a city and region, is unknown and kept. `discovery.regions` applies to hybrid and onsite postings only: the location must name one of the regions, and a location that names no place is kept. The agent import applies the same work mode gate (`modePass`, strict). With no policy nothing is dropped. `discovery.hybridMaxOfficeShare` is enforced by the find mode when it reads the job description, not by code; a user who accepts low touch hybrid lists both `remote` and `hybrid`.
* **Recency keys on the original publish date.** Greenhouse `first_published`, Ashby `publishedAt`; for a known ATS address enrichment replaces any aggregator date with the ATS date. An updated date moves on every repost. The window is `discovery.maxAgeDays` (default 30; `0` turns it off in the pipeline and in every source, which then omit their own recency parameter) plus `seniorityExtensionDays` (default 0) for senior titles.
* **Salary floor.** Only a parsed PUBLISHED yearly band whose stated currency equals `discovery.salaryCurrency` and that tops out below `discovery.salaryFloor` drops a posting. Free text is parsed for the codes USD, GBP, EUR, CAD, AUD, NZD, SGD, CHF and the dollar, pound, and euro signs; a bare `$` is read as USD only for a posting placed in the US. Everything else (another or an unstated currency, pay per hour, month, or pay period, no pay) is unknown, kept, and labeled. Presentation rules for the find mode: show only rows that pass the user's policy, never pad with flagged rows, and show a compensation figure on every row (published, else read from the live listing, else a clearly labeled estimate that never counts as meeting the floor).
* **Discovery is query driven, not company driven.** The pipeline asks which jobs in the market match the user, not what is new at a fixed watchlist. `configs/portals.json` and the workspace seeds only seed the emergent company index.
* **Slug harvest before discovery.** Twelve `site:` patterns across eleven ATS hosts, each with up to three seed roles (36 search calls at most, which matters for a metered key), enumerate unknown tenants into the index before the sources run.
* **Source plugin contract.** Search terms from `roleStrings(ctx)`, title gate from `makeTitleMatcher(ctx)`, policy from `ctx.filters`, tenants from `lib/ats-tenants.js` or `collectors/seed-files.js`. A missing key, flag, seed role, or tenant means `[]` and one log line. Request headers carry `jobe-discovery/1.0 (personal job search)` or a plain browser agent, never a person, email, or account name.
* **Opt in sources stay off by default.** `hiring-cafe` (its robots file disallows the search pattern) and `indeed-camoufox` (launches a stealth browser against a site with no public API; signed out only, stops on any verification page).
* **Dedup is downstream, not upstream.** Every source emits raw postings; `lib/dedup.js` merges URL exact, then exact `dedupKey` = sha1(company slug, normalized role), then MinHash bigram LSH at Jaccard 0.70. Location is left out of the key, so under a remote only policy one requisition listed in several locations collapses; under any other policy the city is part of the merge and of the applied or skipped history match, so the same title in two cities stays two rows. Every remote, country only, or empty location of one employer and title is one row per country; a hybrid location with no city is a row of its own; real cities stay apart. A remote row the US classifier does not place in the US keeps its own place token as the key, so it never merges into the US remote row and still reaches the country gate (cost: two wordings of one such place stay two rows). The report slug follows the same rule (`lib/dedup.js reportSlug`: `{company}-{role}`, plus the city unless the policy is remote only), so two cities never share a report folder, queue row, or tracker row. Known ceiling: a posting whose title or company is written in a non Latin script is discarded at `createPosting` (posting text is ASCII only so dedup keys stay stable), and a non Latin location is read as no location. The manual LinkedIn ingest dedups by the same rule.
* **Cross run history filter.** The pipeline drops any posting whose `dedupKey` matches a requisition already applied to or skipped, whatever source found it (and, outside a remote only policy, in the same city when the queue row carries a `location`). Counted as `applied/skipped` in the filter log; `--include-applied` overrides.
* **Staffing filter.** The shared staffing list is unioned with the user's negative list in one loader (`lib/exclusions.js`) used by the pipeline, the manual ingest, the agent import, and `final-list.js`. `discovery.excludeStaffing: false` turns it off (agencies are a normal channel in some fields).
* **Enrichment is lazy.** The top 300 ranked postings get the job description, compensation, and original date, 8 at a time, cached 30 days. Enrichment rederives work mode, country, and date from the real posting so the strict pass runs on verified data.
* **Discovery is not verification.** A source may only ASSERT a work mode. `linkedin-guest` cards show the company's head office city and the posting cannot be enriched, so every posting from it carries `remoteVerified: false` and the displayed city in `hqLocation`. Only a verification step that read the real posting may set `remoteVerified` true. Only `verifyStatus: "remote"` or a location from the employer's own listing may be presented as remote; `inconclusive` and `unreachable` are not remote.
* **Every LinkedIn guest lead is resolved to the employer's own listing.** Two passes in the find mode: `scripts/resolve-linkedin-to-ats.js` (deterministic: company name to board, then a title match with Jaccard at least 0.5 and a clear margin over the runner up, so it cannot link a different requisition), then an agent sweep for the residue, since the resolver probes only Greenhouse, Lever, and Ashby. Whatever stays unresolved is flagged and verified through `scripts/verify-remote.js` (signed out guest endpoint only). Resolution can also correct the employer shown on the lead.
* **Account safety (hard).** Never automate the user's signed in LinkedIn session unattended. The guest source and both LinkedIn scripts use only the public signed out endpoint. `linkedin-tab` reads an open tab; `linkedin-search` drives the signed in search only when the user explicitly invokes it and is present: human paced, never headless or scheduled, never solve a visible CAPTCHA (the invisible reCAPTCHA node that is always in the page is normal; ignore it). `lib/linkedin.buildSearchUrl` takes work mode, geo, and recency from the profile.
* **Agent fallback.** When `discovery-summary.json.needsAgentFallback` is true (Brave under 100 results, or under 300 postings after dedup) the find mode launches the `jobe-job-discovery` agent with the user's own roles and policy inlined. `lib/agent-import.js` merges its output through the same filters.
* **Auto apply default is Camoufox stealth, not Chrome.** Chrome driven over CDP leaks automation traces that trip detection and email confirmation walls. Flow: fill, glance (screenshot and summary), submit, email confirm loop, record. The agent orchestrates through the state and control files because the Node harness and a mail connector cannot call each other. Headless by default; `--headful` only to watch a run or clear a wall. Ashby boards use a persistent profile warm mode, one run at a time, and a `submit-blocked-spam` tenant is never retried. `--paste` is the fallback for forms behind a sign in wall.
* **The harness answers only from the user's files.** Eligibility questions (work authorization, sponsorship, citizenship, domicile, federal eligibility, clearance, relocation, restrictive covenant) come only from `data/apply-profile.json`; a blank value is surfaced to the user, never guessed. A Yes on `nonCompete` is a warning to the user before submit, never an automatic decision about an employer. EEO declines unless the user opted in with their own values. The location guard follows the profile and blocks nothing without a policy. Free text answers are written by the agent from real evidence and pass through `lib/normalize.js`.
* **Modes beat a long prompt.** 20 files instead of one monolith.
* **Standing rules travel with the profile.** A subagent inherits nothing. The "Standing rules" section of the user's `_profile.md` (and its optional sections Attribution rules, Role posture leads, Verified figures, Known corrections, What not to use in output) is loaded on every command and inlined into every subagent prompt, with the absolute workspace path substituted.
* **Evaluation in blocks A to G** with ghost job detection in Block G. Gate pass scoring runs before resume generation.
* **Archetypes are optional and user defined** (`data/archetypes.json`). None ship; the default is `General`, where evidence ranks by JD keyword overlap. An archetype match is a bonus in selection, never a gate.
* **Positioning reasoning is internal only.** The framework words are banned from output and the renderers refuse a document that contains one (`scanPositioningVocab`).
* **JD grounded tailoring is required.** Resume generation is not "emit the selector's output". `lib/tailor.js` and `scripts/tailor-brief.js` produce the brief (ranked keywords, responsibilities, evidence ranked by fit, honest gaps). JD keywords are counted over the responsibilities and qualifications sections only (the whole text unless both sections are found; English function words are excluded, and the scoped text ends where a bulleted section returns to prose), and the hiring company's name is left out when the caller passes it (`analyzeJD(jd, { exclude: [company] })`; `auditResume` does so from the resume JSON's top level `company`, and `tailor-brief.js` does so when given a `posting.json` or `--url` record). `seniority` is the level word in the JD's first line, or null; it is never read from body text; Block E of the evaluate mode then reframes: lead each entry with the most relevant evidence, restate every bullet in the job description's vocabulary while preserving real figures and inventing nothing, write a role specific summary, pick matching projects, name honest gaps. Keyword overlap alone produces resumes that do not speak to the role.
* **The bullet library is a candidate pool and a floor, not the evidence source.** The deterministic selector reads only the library and the baseline. Generation also reads the user's evidence file (and the user's own work product where it exists) and writes from that. Reordering a fixed pool yields resumes with identical bodies; per JD selection plus the reframe yields real differentiation. `scripts/check-evidence-coverage.js` with `data/evidence-anchors.json` is the drift guard (exit 0 when the file is absent or empty, exit 2 when it exists but does not parse): when a capability is added to the evidence file, add a bullet AND an anchor.
* **Depth over scale.** A bullet about a major body of work must name how it works (the method), not only its size or outcome. `scripts/check-evidence-depth.js` with `data/evidence-depth.json` gates the library and a single resume.
* **Evidence retrieval layer (optional).** `scripts/evidence-index.js` indexes the user's own vocabulary across `evidence.roots`; `tailorBrief` and `buildProfile` credit it so a tool present in the user's work never reads as a gap. It only credits: STATED skills and stated experience stay authoritative and are never stripped because a scan did not find them (most work output is in no scannable folder). Useful only when evidence is plain text on disk; a no op otherwise. Semantic search is optional and external; do not build one into Jobe. See `docs/evidence-retrieval-layer.md`.
* **Anti fabrication.** Every claim traces to the user's evidence. Business figures are user supplied (the Verified figures section), never inferred. Never invent a metric, an employer, a credential, or an answer.
* **Attribution.** Each body of work belongs to one employer or to the projects section, as the user's `companyKeyMap` and Attribution rules say. A personal project is never listed under an employer. `auditResume` checks that the baseline's first employer leads and that entries stay reverse chronological; relevance is expressed by reordering bullets inside an entry, never the entries.
* **No internal names in rendered fields.** `output.forbiddenTerms` lists project names, client names, and codenames; a hit refuses the render. Describe such work by function.
* **Render gates.** Forbidden terms and positioning vocabulary are always fatal. The resume audit, the method depth gate, and the cover letter bar warn by default and block under `--strict` or `JOBE_STRICT_AUDIT=1`. `auditProse` is advisory only and never gives an authorship verdict. The rendered page, not a word count, is the authority on length: `check-docx-pages.js` and `auditResume` gate on `output.targetPages` (no target means no page fill check).
* **Resume rendering.** Summary, Selected Projects, Experience, Skills, Education, Awards. Native Word list bullets, lines kept together, optional `layout: "compact"`. ATS normalization in both renderers: every dash and bullet glyph, smart quotes, and ATS illegal characters are always folded to safe ASCII, and invisible characters and emoji are removed; letters, marks, digits, punctuation and currency signs of every script are kept as written (plus the degree, plus minus, times, divide and numero signs). Plain hyphens are removed only when `output.stripHyphens` is true, and `output.asciiOnly: true` folds accented Latin letters to their base letter, writes out symbols that carry meaning (the micro sign as "u", degree, plus or minus, currency signs) and removes every other script. Paper size and the cover letter date format come from `pageSetup(loadProfile())` (`output.pageSize`, `output.dateLocale`; unset means Letter when the country list is empty or names a country that uses Letter paper (the US, Canada, Mexico, the Philippines and several countries in Latin America), A4 otherwise, and en-US dates). The contact line prints phone, email, location, LinkedIn, `contact.website`, and `contact.github`. Posting text used for dedup keys always strips hyphens, independent of that setting.
* **Role posture.** Flex the resume voice to the posture the role asks for (individual contributor, people leader, senior technical lead) using the user's Role posture leads. Emphasis, not fabrication.
* **Cover letters.** Every letter carries one measurable outcome, one leadership or scope signal, and one decision the work drove (`auditCoverLetter`). When `data/career-narrative.md` holds real content the letter is that chronological career story framed toward the role; otherwise the three paragraph form.
* **Content differentiation.** The cover letter, the "Why this company" answer, and custom questions use different evidence.
* **Batch generation includes an adversarial verify and repair stage.** The batch workflows verify attribution, role posture, method depth, forbidden terms, ATS characters, and cover letter quality after generation, and fix in place. Without the Workflow tool, the batch mode's sequential path applies the same checks.
* **Folder lifecycle (staged buckets, in order).** `verify` (generated; verification pending or failed), `evaluate` (scored and verified; decision pending), `queue` (ready to apply; new evaluations land here), `manual` (a person must finish it), `applied`, `skipped`, `archive` (aged out), `audit`. `manual` is an active parking bucket and files flat, never under a dated archive. `moveReportFolder(slug, bucket)` finds the folder wherever it sits and rewrites the queue entry and the tracker. `locateReportDir` also finds older layouts (flat `reports/{slug}/`, `needs-manual`, `gated`, `non-gated`, dated archives), and every reader uses it, so there is one bucket list.
* **Self cleaning queue.** `scripts/prune-queue.js` runs at the start of every find: it removes queue rows with no folder, archived rows, and rows whose title the user's policy excludes, keeps all applied and skipped history, and never deletes a folder.
* **Multi user workspaces.** People targeting different fields share one install and never see each other's data. With no workspace configured the workspace is the install root, so a single user install needs no setup beyond onboarding.
* **Data contract.** The user layer is never overwritten. The system layer is replaced on install. One exception to state whenever upgrading comes up: a clone made when `data/queries/seeds.json`, `data/companies/negative-list.json`, `data/companies/non-tech-seed.json` and `.claude/settings.local.json` were still tracked must move those four files aside before its first `git pull` (README "Upgrading from an older clone"); never suggest stash, checkout, or a hard reset there. `install-local.sh` copies skill text to `~/.claude/skills/jobe/` and `~/.claude/agents/`, and code, configs, templates, and this guidance file to `~/.jobe/`; it seeds no personal file and never writes the user's own `~/.claude/CLAUDE.md`.
